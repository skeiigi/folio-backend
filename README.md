# Folio API

Node.js API для творческой платформы Folio. Автор публикует иллюстрации, анимацию и настоящие GLB-модели, настраивает профиль и услуги; заказчик изучает портфолио и отправляет бриф. API и [React-клиент](https://github.com/skeiigi/folio-frontend) развёртываются отдельно.

## Быстрый запуск

Нужен Node.js 22. В каталоге этого репозитория:

```bash
npm ci
npm run setup
npm run db:migrate
npm run db:seed
npm run dev
```

`setup` создаёт локальный `.env` со случайным ключом токенов. В режиме разработки используется PGlite — настоящая PostgreSQL-совместимая база в `.data/postgres`, без Docker и облачного аккаунта. API работает по адресу `http://localhost:4100`, проверка готовности — `/ready`, контракт — `/api/v1/openapi.json`. Фронтенд запускается отдельно по его README. При желании используйте PostgreSQL 16 через `docker compose up -d`, установите `DB_MODE=postgres` и `DATABASE_URL=postgresql://folio:folio_dev_password@localhost:5432/folio` в `.env`, затем повторите миграцию и заполнение.

`db:seed` выполняется **только вручную**. Он добавляет трёх авторов, шесть работ (включая две вращаемые 3D-модели), четыре услуги и три брифа. Локальные аккаунты: `anton@folio.test` (заказчик), `mira@folio.test`, `lea@folio.test`, `nikita@folio.test` (авторы), `admin@folio.test`. Пароль для всех: `FolioDemo2026!` или значение `DEMO_PASSWORD` из `.env`. Не запускайте сидирование для публичной базы с этим паролем.

## Возможности и границы MVP

- Регистрация, вход, роли заказчика, автора и администратора; один человек может быть и заказчиком, и автором. Пароли хранятся как salted scrypt hash, токены проверяются по состоянию аккаунта в базе.
- Каталог с поиском, фильтрами по типу и стилю и пагинацией. Публичные профили показывают специализацию, услуги, диапазоны цен, сроки и работы.
- Черновик, редактирование и публикация работы. Обязательны обложка и, для 3D, валидный GLB; для анимации — превью. Тип и сигнатура загружаемого файла проверяются на сервере.
- Автор может переставлять и скрывать секции профиля, менять колонки, тему и акцентный цвет через ограниченный JSON `layoutConfig`. Произвольный HTML/JavaScript пользователя не исполняется.
- Бриф создаётся для выбранного автора с бюджетом, сроком и закрытыми референсами. История статусов и допустимые переходы проверяются по роли и владельцу.
- Модератор может блокировать аккаунты и снимать работы с публикации.
- Если настроен почтовый сервис или CRM/BPMS, задания доставки записываются в `event_outbox` в одной транзакции с брифом. Без внешнего провайдера работает внутренний центр брифов, а письма не отправляются.

Таблицы предметной области: `users`, `creator_profiles`, `artworks`, `media_files`, `services`, `briefs`. Технические таблицы: `storage_objects`, `brief_events`, `event_outbox`, `schema_migrations`. Для `media_files` база гарантирует связь ровно с одной работой или одним брифом. Права на изображения, условия оплаты и юридическое оформление заказов остаются предметом прямой договорённости сторон — платежей и автоматических договоров в MVP нет. [Соответствие учебным работам](docs/COURSEWORK.md).

## API

Основные пути с префиксом `/api/v1`:

| Действие | Метод и путь |
| --- | --- |
| Регистрация / вход | `POST /auth/register`, `POST /auth/login` |
| Текущий пользователь / профиль | `GET /auth/me`, `GET /me/profile` |
| Авторы / публичный профиль | `GET /creators`, `GET /creators/:id` |
| Работы / одна работа | `GET /artworks`, `GET /artworks/:id` |
| Черновик и публикация | `POST /artworks`, `POST /artworks/:id/media`, `POST /artworks/:id/publish` |
| Услуги автора | `GET /me/services`, `POST /services`, `PATCH /services/:id` |
| Брифы | `POST /briefs`, `GET /me/briefs`, `GET /briefs/:id`, `PATCH /briefs/:id/status` |
| Референс | `POST /briefs/:id/attachments`, `GET /media/:id/content` |

Закрытые запросы передают `Authorization: Bearer <token>`. При создании брифа `clientUserId` определяется по токену, а не по форме. `GET /media/:id/content` отдаёт опубликованные работы публично, а черновики и референсы только участникам с правом доступа. Полный машинный контракт: `GET /api/v1/openapi.json`.

## Проверка

```bash
npm run check
npm test
```

Интеграционные тесты запускаются на изолированной базе PGlite и проверяют регистрацию, права доступа, жизненный цикл брифа, файлы, публикацию GLB, CORS и требования production-конфигурации. CI выполняет те же команды при каждом push/PR.

## Хостинг

Готовый `render.yaml` запускает Node-сервис, миграцию и health check. Для постоянной базы подходит отдельный управляемый PostgreSQL, например Neon; файлы по умолчанию тоже хранятся в PostgreSQL, чтобы не зависеть от временного диска веб-сервиса. Подробные переменные и порядок публикации: [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md). Наличие конфигурации не означает, что облачная версия уже опубликована.
